## Implementation Summary

The transfer-count calculation function `calculate_transfer_counts` was already implemented in `runtime/src/playlist_bridge/jobs/runner.py` but was using an outdated `decision_type` field that no longer exists in the `MatchDecision` model. The implementation was updated to use the current model fields (`status` and `selected_candidate`) to determine match status.

### Changes Made

1. **Updated `calculate_transfer_counts` in `runtime/src/playlist_bridge/jobs/runner.py`:**
   - Replaced logic that used `decision.decision_type` with logic that uses `decision.status` and `decision.selected_candidate`
   - Tracks with `status == "matched"` and `selected_candidate is not None` are counted as `matched`
   - Tracks with `status == "unmatched"` are counted as `unmatched`
   - Tracks with no decision are counted as `unmatched`
   - Tracks with availability `"unavailable"` are counted separately
   - Updated docstring and examples to match the current API

2. **Updated `runtime/tests/unit/jobs/test_transfer_counts.py`:**
   - Rewrote all test cases to use the current `MatchDecision` model structure
   - Created proper `MatchScore` and `SpotifyCandidate` objects for matched tracks
   - Verified that counts sum to the total source track count
